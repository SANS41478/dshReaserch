# 逐包精读解读规范（DeepSeek Harness 解构站）

你要为分配到的若干 npm 包，各写一份**架构层**深度解读。
读者是刚接触 dsh 的人：他要的是「读完能跟别人讲清楚这个包在系统里的位置和职责」，**不是**「读完能改它的代码」。
所以重心放在**职责、边界、协作关系、关键机制的意图**上，不要写成 API 手册或逐行代码注释。

## 输入

仓库根：`D:/下载的软件在这里！/deepseek-harness源码/deepseek-harness`
每个包的事实底料已生成：`D:/临时/dsh研究/data/deep/brief/<group>__<dir>.txt`

底料包含：README 全文、每个源文件的导出符号（带行号、附带类成员）、`static inject` 声明、
`declare module` 块、package.json、cordis.patch.yml。

**底料只是索引。你必须真的打开源码读。** 尤其是：
- `src/index.ts`（插件入口，`apply()` 里做了什么）
- 体积最大的那个源文件（通常藏着真正的机制）
- 任何定义了 Cordis Service 的文件（`class X extends Service`）

## 输出

写**一个** JSON 文件到 `D:/临时/dsh研究/data/deep/out/<BATCH>.json`，
内容是一个数组，每个元素对应一个包，**字段顺序固定**，必须严格是合法 JSON（双引号、无尾逗号、无注释、无 markdown 围栏）。

```json
{
  "group": "core",
  "dir": "agent",
  "short": "agent",
  "oneLiner": "一句话定位，≤45 字，说清它占领哪块职责",
  "why": "为什么必须有这个包。回答：如果把它删掉/不加载，系统的哪一块会塌，塌成什么样。200-300 字。要有具体后果，不要写「提供统一抽象」这类空话。",
  "position": "它在系统里的位置。回答三件事：① 谁会调用它（上游）② 它依赖谁（下游）③ 数据是往哪个方向流的。250-350 字。要写出具体的包名和服务名（如 ctx.agents、ctx.session）。",
  "inside": "内部结构。按文件/类/机制分块讲清楚：这个包肚子里有哪几个主要部件，各自干什么，它们怎么串起来。450-600 字。这是全文最重的一段，要具体到类名、函数名、事件名。",
  "boundary": "职责边界。回答：哪些事明确归它管，哪些事明确不归它管（推给了哪个兄弟包）。200-300 字。边界要写清「划线依据」——为什么这么划。",
  "tour": [
    { "file": "packages/core/agent/src/index.ts", "line": 42, "sym": "AgentRegistry.create", "note": "40-70 字：这一行为什么值得看，它体现了上面讲的哪个机制" }
  ],
  "gotchas": "坑、限制、反直觉的地方、README 里明说的 Known Limitations。150-250 字。",
  "analogy": "通俗复述。用一个日常类比把这个包的角色讲明白，让完全不懂的人也能建立直觉。120-180 字。"
}
```

### 字段质量要求（逐条自检）

- **`tour` 必须真实**：3-5 条。每条的 `file` 用仓库相对路径（正斜杠），
  `line` 是你**实际打开该文件确认过**的行号，指向的必须是那个类/方法/常量的定义处或关键实现处。
  不许凭底料猜行号——底料的符号表可能不准，必须打开文件核对。
  优先挑能体现「为什么这样设计」的行，而不是随便第一行。
- **`inside` 要具体到名字**：出现类名、方法名、事件名、ctx key。禁止「包含若干工具函数」「处理相关逻辑」这类填充。
- **`why` 要有反事实**：写「不加载它，X 就 Y」，而不是「它很重要」。
- **`position` 要写出真实的数据流方向**：谁把数据递给谁，谁回调谁。
- 全文**中文**；技术专有名词（Cordis、Service、inject、包名、ctx key、事件名）保留英文原文。
- 如果某个包确实很小（<200 行、纯配置/纯注册），各段按比例缩短，但**不要**因为小就写成一句话——
  仍要说清它注册了什么、为什么独立成包。
- **绝对不要**把 README 的 Summary 抄一遍当 `inside`。README 是「怎么用」，你要写的是「它在系统里是什么」。

## 禁止

- 不要写「本包提供了一系列功能」「方便开发者使用」「是系统的重要组成部分」这类没有信息量的话。
- 不要编造源码里不存在的类名/事件名/文件名。不确定就打开看。
- 不要输出 JSON 之外的任何文件。

## 完成后

用一句话回报：写了几个包、哪些包的解读你觉得依据不足（比如 src 为空、纯类型包）。
